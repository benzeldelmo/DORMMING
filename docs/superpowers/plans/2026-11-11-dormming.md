# DormMing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the DormMing laptop demo: a phone-first React app over a Java (Spring Boot) API whose domain classes show abstraction, inheritance, polymorphism and encapsulation, covering all 13 brief features.

**Architecture:** React (Vite) calls a Spring Boot REST API on `localhost:8080` with a bearer JWT. All money rules live in `com.dormming.domain`. Storage, login, sync and AI each sit behind an interface with a local implementation (in-memory, self-signed JWT, polling, demo assistant) and a cloud one (Supabase JDBC, Supabase Auth, Supabase broadcast, Gemini) selected by Spring profile / env vars.

**Tech Stack:** Java 21 language level on installed JDK 27, Maven 3.10, Spring Boot (latest stable from start.spring.io: web, security, oauth2-resource-server, validation), JUnit 5 + AssertJ. React + Vite (JavaScript, not TypeScript), Tailwind CSS v4, shadcn/ui, lucide-react, react-router-dom, @tanstack/react-query, qrcode.react, vitest.

**Spec:** `docs/superpowers/specs/2026-11-11-dormming-design.md` (brief: `PROJECT_BRIEF.md`)

## Review Focus

1. Peso input like `1,000`, `₱1000`, `1.234`, `0`, `abc` → clean error message, nothing saved. Tests in Task 1 (`Money`), Task 8 (API 400), Task 13 (`parsePesos`).
2. Shared expense where the payer is not a participant (paid for others) → every participant owes the payer their full share. Test in Task 4.
3. Leaving: member with an open balance is blocked; creator leaving passes the creator role to the next member by join order; last member leaving deletes the dorm. Tests in Task 7.
4. Payment larger than the open debt, to yourself, or to a non-member → 400 with a message, balances unchanged. Tests in Task 9.
5. Missing or expired token → 401; the frontend clears the token and routes to `/login` instead of a blank screen. Tests in Task 6 (backend) and manual check in Task 14.

### Task 2: Split strategies

**Files:**
- Create: `domain/split/{SplitStrategy,SplitType,EqualSplit,CustomSplit,ItemizedSplit,ReceiptItem}.java`, `domain/user/UserId.java`
- Test: `domain/split/SplitStrategyTest.java`

**Interfaces:**
- Consumes: `Money`.
- Produces:
  - `record UserId(String value)` (non-blank).
  - `interface SplitStrategy { Map<UserId, Money> split(Money total, List<UserId> people, UserId payer); SplitType type(); }` — result is a `LinkedHashMap` in `people` order, values sum exactly to `total`. `payer` may be null. Throws `IllegalArgumentException` if `people` empty, has duplicates, or `total` not positive.
  - `enum SplitType { EQUAL, CUSTOM, ITEMIZED }`
  - `EqualSplit()`; `CustomSplit(Map<UserId, Money> amounts)`; `ItemizedSplit(List<ReceiptItem> items, Money extras)` with `Map<UserId, Money> itemSubtotals(List<UserId> people, UserId payer)` public for the receipt screen.
  - `record ReceiptItem(String name, Money price, List<UserId> sharers)` (name non-blank, price positive, sharers non-empty).

Rounding rule (spec §8): leftover centavos go one each to people other than the payer, in `people` order; if payer is null or not in the list, to people in order.

ItemizedSplit algorithm:
1. Split each item among its sharers with the EqualSplit rule → per-person item subtotals.
2. Require `sum(item prices) + extras == total`, else IAE `"Items and extras must add up to the total"`.
3. Distribute `extras` in proportion to subtotals: `base_i = trunc(extras × sub_i / itemsSum)`; hand the remaining centavos (sign of `extras`) one each by largest absolute fractional remainder, ties by `people` order.
4. Every sharer must be in `people`, else IAE. People with no items get 0.
